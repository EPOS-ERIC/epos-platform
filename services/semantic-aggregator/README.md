# Semantic Aggregator

Foundation for a service that will import EPOS-DCAT-AP Turtle metadata into Metadata Lifecycle and periodically aggregate published metadata from Metadata Lifecycle and Data Retriever into versioned RDF graphs in a triplestore.

This initial service exposes gRPC on port 8300, including the standard health service, the experimental `DatasetImportService.ImportDatasets` RPC, and `ResourceImportService.ImportResources` for v1 datasets, `schema:SoftwareApplication` and `schema:SoftwareSourceCode`. Resource imports derive their destination group from each referenced `skos:Concept` category's `skos:inScheme`. A group scheme declares its top-level concept using legacy `topLevelConcept` metadata or `skos:hasTopConcept` with the `dataset-theme`, `facility-theme` or `software-theme` facet. Other `skos:ConceptScheme` resources are vocabulary schemes and are ignored unless an imported resource uses one as its category scheme. Scheme IRIs are durably associated with lifecycle-created group IDs; categories are similarly created once per scheme/group. A resource may reference categories from only one scheme. `group_id` remains a deprecated protobuf wire field and is ignored; Gateway no longer exposes it. DatasetImportService retains its existing caller-supplied group behavior. A Turtle reader loads documents into isolated in-memory Jena models. The service does not yet connect to a triplestore or generate graphs. Health reports process liveness, not dependency readiness. Set `GRPC_PORT` to change the listening port and `METADATA_LIFECYCLE_ADDR` for the upstream gRPC address (default `localhost:5000`).

## Experimental dataset import

The shared contract is `packages/protobuf/semantic_aggregator/v1/import.proto`. Provide Turtle bytes (up to 10 MiB), an absolute base URI, a registered mapping ID/version, a Metadata Lifecycle group UUID, and trusted `x-epos-user-id` gRPC metadata. Only trusted internal clients such as Gateway should supply this metadata; Metadata Lifecycle performs resource authorization. The entire input is checked before any write, and input with disconnected RDF subjects or unsupported fields is rejected. Downloadable distributions require a title, description, explicit `DOWNLOADABLE_FILE` type, download or access URL and format; if both URLs are present they must match. Web service distributions support a single HTTP Hydra operation with a method and output format, optional Hydra API documentation, and spatial and temporal coverage. HTTP(S) URI templates may use `{name}` placeholders in the path and a trailing `{?name,...}` query expansion, or `{&name,...}` when a query already exists. Each variable requires a matching, explicitly typed Hydra parameter; path parameters must be marked required. Supported types are `xsd:string`, `xsd:boolean`, `xsd:integer`, `xsd:long`, `xsd:float`, `xsd:double`, `xsd:decimal` and `xsd:dateTime`. Numeric and date-time bounds and defaults are validated; numeric enumerations are supported, and values that cannot be represented by the target types are rejected. Date-time values require an explicit timezone and layouts use Metadata Lifecycle tokens such as `YYYY-MM-DDThh:mm:ss`. Other expansion forms and parameter types are rejected. WMS/WFS/WMTS and non-dataset resources are not yet supported.

Dataset publisher, contact and category IRIs, web-service provider and contact IRIs, and software creators and contacts can refer to existing Metadata Lifecycle entities. Supply a `references` binding for each `(kind, IRI)` with the corresponding existing UUID. For contacts without a binding, the RDF description must supply both email and role: the service reuses an existing exact `(email, role)` match or creates a contact through Metadata Lifecycle. Its unique constraint handles concurrent creations; on a conflict the service re-reads the contact. The actor needs contact-read permission for lookup and contact-management permission to create a missing contact. Bindings must be unique, use absolute IRIs and nonzero canonical UUIDs; UUIDs are never derived from IRIs.

An unbound organization with a supported RDF name can be created through Metadata Lifecycle with its supported address and optional metadata. If an organization with the same name already exists, or another process creates it concurrently, the importer requires an explicit binding rather than assuming that the RDF IRI has the same identity. If both `name` and `legal_name` are supplied they must agree, since the destination exposes a single name. Organization creation requires global organization-management permission. Organization identifiers, parents and linked contacts are not yet imported.

For an unbound category with an RDF name and no hierarchy, the importer creates a root category in the requested group. If a root category with the same name already exists, the importer requires an explicit binding: a matching name alone does not establish RDF identity. A concurrent name conflict is reported rather than automatically reused. Category creation requires the actor's group category-management permission. `skos:broader`, category schemes and other unsupported category properties are rejected, so categories with hierarchy are not silently flattened to roots.

Before writes, the service validates supported RDF and checks explicitly bound or reused entities through Metadata Lifecycle, including the category's group. This preflight does not lock entities and cannot guarantee that later upstream validation will succeed. `contacts` in the response reports the IRI and UUID of each automatically reused or created contact, with a `created` flag; `categories` and `organizations` report created entities and their IRI/UUID associations. On a failure, `failure.phase` identifies organization creation, contact resolution, category creation or dataset creation, and previously completed operations remain in the response. A lost or uncertain contact creation response can be reconciled through its unique email/role key. Uncertain organization or category creation requires checking the upstream entity and providing an explicit binding before retrying. **Dataset creation is not idempotent**: if a response is lost or a later dataset fails, reconcile dataset IDs before retrying the file.

For referenced entities, an RDF description can supply organization name/legal name, logo, page URL, email, LEI and a linked postal address (street, locality, postal code and country), or contact email and role. The profile's optional `entity_mappings` section configures these RDF types and predicates, including organization address paths. ResourceImportService extracts those supported fields and tolerates additional descriptive RDF such as external identifiers, membership and contact languages; Metadata Lifecycle does not store those fields. Mapped fields still require their configured type and cardinality. When reusing an existing entity, supplied values must match its canonical metadata; a mismatch prevents any writes. URL fields accept RDF IRIs or absolute URI literals; other fields require untagged strings. Existing entities are not updated.

The RPC creates datasets sequentially and stops at the first upstream error. The response lists successful resource/version IDs and, when applicable, the failed subject, gRPC code and whether the upstream outcome is unknown. The operation is **not transactional or idempotent**: successful creates remain after a later failure, and a lost response or an unknown outcome may also hide a successful create. Do not blindly retry the same file; reconcile upstream resources first. This experimental RPC is not yet exposed through Gateway and does not replace the existing Metadata Lifecycle Turtle importer.

## Development

```sh
make dev
make build
make test
make lint
```

Tilt runs the service on the internal development network. The service uses Java 25 LTS, Maven and Apache Jena. Local Maven builds require a JDK 25 installation and Docker for Buf code generation; the Tilt development image provides the JDK. `make build` and `make test` generate Java types from the shared protobuf contracts; Tilt generates them at startup. `make lint` recompiles with Java compiler warnings enabled; it is not a full static analysis tool.

## Persistent identity and import caveats

`IDENTITY_STATE_DIR` stores IRI→UUID associations per mapping profile and destination group, plus a locked `skos:ConceptScheme` IRI→group UUID registry for ResourceImportService. The registry is required because Metadata Lifecycle allocates group IDs; IDs are not derived from scheme IRIs. A deleted mapped group/category is not recreated automatically and must be reconciled by an operator. The state volume (`semantic-aggregator-state` in development) is local identity metadata, not a second triplestore. Multiple datasets are processed sequentially, and dataset IDs require manual reconciliation after uncertain failures.

## Fuseki development setup

The development Compose stack starts Apache Jena Fuseki 5.6 with a persistent dataset named `ds`, exposed through the SPARQL Graph Store protocol at `http://semantic-aggregator-fuseki:3030/ds/data`. The stack uses the local-only default `ADMIN_PASSWORD=semantic-aggregator-dev`; override this environment variable rather than editing container state manually, and never commit real credentials. Fuseki's container health check verifies `/$/ping`; Graph Store operations use its write-enabled endpoint.

The service remains usable for experimental ingestion if the triplestore is unavailable. The optional CI Compose profile is `semantic-fuseki`; it uses a separate volume and a local-only default password. Fuseki and identity volumes are not removed by `make clean`.

The Graph Store adapter, published-catalog reader, protobuf-to-RDF builder and refresh orchestration are implemented. Set `AGGREGATION_REFRESH_INTERVAL` to a positive ISO-8601 duration such as `PT15M` to enable a background refresh; it requires `TRIPLESTORE_REPOSITORY_URL`, `TRIPLESTORE_USERNAME` and `TRIPLESTORE_PASSWORD`. The scheduler is disabled by default, refreshes v1, v2 and v3 independently, and retries failed graph versions at the next interval. The builder currently exports published datasets with their immutable resource/version identity, basic dataset metadata, persistent identifiers, linked-entity references, downloadable distributions and Web Service endpoint/configuration metadata, plus basic software application and source-code metadata. The remaining EPOS-DCAT-AP shapes are not exported yet. The orchestration builds before writing, checks the builder's declared resource coverage, re-reads the inventory and uses separate named graphs for v1, v2 and v3. Its overlap guard is process-local; it does not coordinate multiple replicas. Discovery currently has no pagination or consistent-snapshot API: its complete response is bounded at 64 MiB in the client and failures abort the read. Comparing inventories detects some changes but is not a transactional upstream snapshot, and an interrupted or failed Graph Store request can have an uncertain outcome.

## Mapping profiles

The bundled `epos-dcat-ap` profile has dedicated versions 1, 2 and 3. Version 1 preserves the full dataset and software mappings from `src/main/resources/mappings/epos-dcat-common.yaml`. Versions 2 and 3 map their common Dataset and Distribution paths, including `dcat:startDate`/`dcat:endDate` temporal coverage, but deliberately do not map `dcat:accessService` or `dcat:DataService`: the importer cannot represent that topology. The legacy `epos-dcat-common` version 1 profile remains bundled for existing callers. Each profile has a unique `id` and positive `version`, a dataset RDF type and the supported target fields with absolute-IRI paths. Optional `parameter_roles` entries associate RDF property values with Metadata Lifecycle roles; recognized roles are validated against parameter types and options before writing. Paths can traverse a linked resource or blank node. Source metadata fields are optional in a profile; distribution, web-service and parameter paths must each be provided as a complete set when enabled. The Java mapper owns the semantics of each target field, including cardinality, temporal conversion, identifier grouping and validation; adding arbitrary target fields or transformations requires code changes.

The optional `primary_identifier` mapping preserves a dataset's `dct:identifier` as a Metadata Lifecycle persistent identifier. Its configured `string_type` and `uri_type` distinguish RDF `xsd:string` from `xsd:anyURI`; these are mapping-specific marker types, not inferred DOI or URI schemes. The RDF subject IRI is distinct from this property and dataset creation is still not idempotent. Profiles without this section keep their previous behavior.

To register additional profiles at startup, set `MAPPINGS_DIR` to a directory of `.yaml` or `.yml` files in the container. Copy the bundled file as a template and change its `id`, `version`, RDF type and paths as needed. Files are loaded in name order, in addition to the bundled mapping. Duplicate ID/version pairs, unsupported fields and invalid paths cause startup to fail. Profiles are currently loaded at startup only; there is no registration RPC yet.
